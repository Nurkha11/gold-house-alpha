# Архитектура аутентификации и ролей

## Цель

Вынести идентификацию пользователя и проверку полномочий на backend. Клиент показывает интерфейс, но не принимает окончательных решений о доступе.

## Роли

- `buyer` — ищет недвижимость, сохраняет объекты и создаёт заявки на просмотр.
- `owner` — создаёт и редактирует только свои объявления, видит связанные заявки в разрешённом объёме.
- `admin` — модерирует объявления и справочники в пределах выданных полномочий.
- `system` — фоновые задачи, уведомления и интеграции; не является интерактивным пользователем.

Один пользователь может иметь несколько ролей. Назначение `admin` выполняется только доверенной серверной операцией.

## Идентичность

Основной идентификатор — неизменяемый `user_id` UUID. Телефон служит способом входа, но не первичным ключом бизнес-данных.

Поток входа:

1. Клиент запрашивает OTP для нормализованного телефона.
2. Backend применяет rate limit и создаёт одноразовый challenge.
3. Пользователь отправляет OTP.
4. Backend проверяет срок, число попыток и одноразовость.
5. Backend возвращает короткоживущий access token и ротируемый refresh token.
6. Каждый защищённый endpoint заново проверяет токен, роль и принадлежность ресурса.

## Сессии

- access token: 10–15 минут;
- refresh token: до 30 дней, хранится в защищённом хранилище устройства;
- ротация refresh token при каждом обновлении;
- повторное использование старого refresh token завершает семейство сессий;
- logout отзывает текущую сессию; «выйти со всех устройств» — все сессии пользователя.

На web refresh token предпочтительно хранить в `HttpOnly`, `Secure`, `SameSite` cookie. На Android/iOS — в SecureStore/Keychain/Keystore, а не в обычном local storage.

## Авторизация

Используется сочетание RBAC и проверки владения:

```text
allow = authenticated
        AND role permits action
        AND resource ownership/scope permits action
        AND resource state permits transition
```

Примеры:

- owner может менять `draft` только своего объявления;
- admin может модерировать, но не подменять владельца;
- buyer видит только свои заявки на просмотр;
- системная отправка уведомлений использует отдельную service identity.

## Административный доступ

- отдельное назначение роли;
- обязательная MFA;
- короткая административная сессия;
- журналирование входа, просмотра чувствительных данных и каждой мутации;
- опциональное разделение `moderator`, `support`, `super_admin`.

## Восстановление и блокировка

- лимит OTP по телефону, IP и устройству;
- временная блокировка после серии ошибок;
- отзыв сессий при смене телефона или подозрении на компрометацию;
- ручная процедура восстановления admin-доступа вне клиентского приложения.
