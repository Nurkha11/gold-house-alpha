# Workflow заявки на просмотр

## Статусы

```text
requested
  → proposed
  → confirmed
  → completed

requested/proposed/confirmed → cancelled_by_buyer
requested/proposed/confirmed → cancelled_by_owner
requested/proposed → expired
confirmed → no_show
```

## Создание

Buyer выбирает объект, timezone и один или несколько временных интервалов. Backend:

1. проверяет доступность публичного объекта;
2. связывает buyer, property и owner из доверенных данных;
3. предотвращает дубликат через idempotency key;
4. сохраняет `requested`;
5. создаёт уведомление owner без преждевременного раскрытия лишних данных.

## Согласование

Owner подтверждает один интервал или предлагает другой. Buyer подтверждает предложение. При финальном подтверждении backend транзакционно проверяет отсутствие пересечения и создаёт confirmed interval.

## Контактные данные

До `confirmed` стороны видят только display name и необходимые сообщения. Телефон/точный адрес раскрываются по явно утверждённой продуктовой политике, предпочтительно непосредственно перед подтверждённым просмотром.

## Конкурентность

- уникальное ограничение/lock для подтверждённых интервалов объекта;
- optimistic version для заявки;
- повторный confirm идемпотентен;
- изменение времени создаёт новый proposal, а не молча переписывает историю.

## Отмена и завершение

Отмена требует причины-кода; уведомляется другая сторона. Фоновая задача переводит неподтверждённые заявки в `expired`. `completed`/`no_show` задаётся после времени встречи и попадает в audit.

## Интеграция календаря

Создание внешнего календарного события выполняется после `confirmed` через outbox/job. Сбой календаря не отменяет сохранённую заявку; статус синхронизации хранится отдельно. Участникам нельзя отправлять календарные приглашения до явного подтверждения.
